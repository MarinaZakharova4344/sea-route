# Схема данных (черновик на согласование)

Все допущения из записки заказчику учтены. Любой вариант ответа заказчика не потребует переделки таблиц.

## Общая картина

```
users ──< shipments >── clients
              │   └──── directions
              ├──< containers
              ├──< finance_lines >── counterparties
              ├──< change_log
              └──1 shipment_metrics   (готовые расчёты, обновляются с задержкой)

settings            (пороги: 2 дня, 10 %, срок оплаты)
analytics_refresh   (когда аналитика обновлялась в последний раз)
```

`──<` значит «один ко многим»: у одной перевозки много контейнеров, много строк доходов и расходов.

## Таблицы

### users: пользователи
| Поле | Смысл |
|---|---|
| email, имя | вход и отображение |
| password_hash | пароль хранится только в зашифрованном виде |
| role | `manager` или `director` (на этом строится проверка прав) |

### clients: клиенты
Название, контактное лицо, телефон/e-mail.

### counterparties: контрагенты (перевозчики, терминалы, брокеры)
Название, тип (`carrier`, `terminal`, `broker`, `other`).

### directions: направления
Порт отправления, порт назначения. Например, «Шанхай → Новороссийск». По этой таблице группируется аналитика «по направлениям».

### shipments: перевозки (главная таблица)
| Поле | Смысл |
|---|---|
| number | номер перевозки (например, SR-0042) |
| client_id, direction_id | кто заказал и куда везём. **Можно оставить пустыми** (черновик) |
| manager_id | ответственный менеджер (нужен для варианта «менеджер видит только свои») |
| cargo_description | описание груза |
| status | `draft`, `booked`, `in_transit`, `arrived`, `closed`, `cancelled` |
| planned_departure / actual_departure | плановая и фактическая дата отправления |
| planned_arrival / actual_arrival | плановая и фактическая дата прибытия |
| finance_closed_at | дата финансового закрытия (пусто, пока менеджер не нажал «Закрыть финансово»; от этого зависит «предварительно / окончательно») |
| created_at | когда создана |
| updated_at, updated_by | когда и кем **сведения о перевозке** обновлены последний раз (для метки «не обновлялась N дней») |

Все даты (отправление, прибытие, финансовое закрытие) хранятся, поэтому любой ответ заказчика на вопрос «к какому периоду относить перевозку» не меняет схему. Сейчас по умолчанию: дата **фактического прибытия**.

Логистический статус (`status`) и финансовое состояние (открыта или закрыта финансово) разделены: груз может быть доставлен, а расчёты ещё нет.

### containers: контейнеры и груз
Перевозка, номер контейнера (может быть пустым), тип (20'/40'), вес, комментарий.

### finance_lines: доходы и расходы построчно
| Поле | Смысл |
|---|---|
| shipment_id | к какой перевозке относится |
| kind | `income` (доход) или `expense` (расход) |
| counterparty_id | клиент или подрядчик (для дохода часто сам клиент) |
| description | за что (например, «Морской фрахт») |
| planned_amount | плановая сумма (для незапланированного расхода 0) |
| actual_amount | фактическая сумма; **пусто, пока счёт не пришёл** |
| is_unplanned | `true` для расхода, которого не было в плане (например, хранение в порту); нужен, чтобы отличать перерасход от внеплановой статьи |
| currency | RUB (одна валюта согласована; поле оставлено как задел) |
| payment_status | `unpaid`, `partial`, `paid` |
| paid_amount, due_date | сколько оплачено и срок оплаты (нужно для просроченных счетов) |
| paid_at | дата оплаты (для показателя «Оплаты клиентов» по месяцам) |

### change_log: история изменений
Руководитель видит в карточке перевозки, **кто, когда и что изменил**. Записывается при каждой правке ключевых полей: даты, статус, суммы (план и факт), статус и дата оплаты, финансовое закрытие.

| Поле | Смысл |
|---|---|
| shipment_id | к какой перевозке относится |
| changed_by | кто изменил (пользователь) |
| changed_at | когда |
| field | что изменено (например, «Дата прибытия», «Факт: Перевозчик Океан») |
| old_value, new_value | было и стало |

Пример записи: «14:05, Иван: Дата прибытия 10.10 → 15.10». Это связывает изменение в учёте с изменением в аналитике: руководитель видит не только новую задержку, но и что именно её вызвало.

### shipment_metrics: готовые расчёты по перевозке
Пересчитывается по расписанию или кнопкой. Именно из неё читает аналитика руководителя.

| Поле | Смысл |
|---|---|
| revenue | доходы (факт, иначе план) |
| cost | расходы (факт, иначе план) |
| margin | revenue − cost |
| is_preliminary | `true`, пока нет финансового закрытия (`finance_closed_at` пусто) или есть расходы без факта |
| result_date | дата, к которой относится результат (по умолчанию дата фактического прибытия); пусто, если груз ещё не доставлен |
| delay_days | на сколько дней задержка |
| overrun_pct | перерасход от плана, % |
| has_overdue_payment | есть просроченный неоплаченный счёт |
| stale_days | сколько дней перевозка не обновлялась (считается только для активных) |
| missing_fields | какие важные поля не заполнены |
| attention_reasons | список причин «требует внимания»: опоздание, перерасход, просрочка оплаты, пустые поля, нет обновлений |
| calculated_at | когда рассчитано |

### settings и analytics_refresh
`settings` хранит пороги (опоздание 2 дня, перерасход 10 %, «не обновлялась» 5 дней), чтобы менять их без правки кода. `analytics_refresh` хранит время последнего обновления для отметки «данные на HH:MM».

## Как это закрывает допущения

| Вопрос | Как отражено в схеме |
|---|---|
| 1. Маржа | И план, и факт хранятся; расчёт «факт, иначе план» делается в `shipment_metrics` |
| 2. Внимание | Пороги в `settings`; причины сохраняются в `attention_reasons` |
| 3. Права | `role` в `users`; `manager_id` у перевозки уже есть |
| 4. Валюта | Поле `currency` со значением RUB |
| 5. «Выглядит лучше, чем работает» | Считается из `shipment_metrics` по клиентам и направлениям |
| 6. Период | Даты в `shipments`; `result_date` в `shipment_metrics` |
| Ситуация 1: предварительно / окончательно | `finance_closed_at`, `is_unplanned`, `is_preliminary` |
| Ситуация 3: сентябрь → октябрь → ноябрь | `result_date` (доставка) для маржи, `paid_at` для оплат |
| Ситуация 4: актуальность данных | `updated_at` у перевозки, `stale_days`, порог в `settings` |

## Пример: одна перевозка

Перевозка SR-0042, клиент «Рассвет», Шанхай → Новороссийск, статус `in_transit`, плановое прибытие 10.10, факта нет.

| Тип | Контрагент | План | Факт | Оплата |
|---|---|---|---|---|
| income | Рассвет | 5000 | 5000 | paid |
| expense | Перевозчик «Океан» | 3500 | 3900 | unpaid |
| expense | Терминал | 400 | пусто | unpaid |

Расчёт: revenue = 5000; cost = 3900 + 400 = 4300 (факт, иначе план); margin = 700; `is_preliminary = true` (у терминала нет факта, перевозка не закрыта); `overrun_pct` = 11 % по перевозчику, значит причина «перерасход».
